# P1 operator foundation

Work started 2026-10-03. Core lifecycle, durable instance/operation CRDs, Helm packaging and recovery are implemented. P1 acceptance completed on 2026-10-04 in a fresh two-node kind cluster, with 111 passing unit tests, no skips, every lifecycle/upgrade/recovery gate and successful teardown. Final review added stricter Pod ownership fencing and six regressions; the final implementation passed the complete fresh suite. Milestones 0–4 together define the initial useful release.

## Framework spike

The spike pins `KubeOps.Operator` 13.3.1 with KubernetesClient 19.0.2. Its [release source](https://github.com/dotnet/dotnet-operator-sdk/tree/v13.3.1) defines the APIs used here. Controllers and finalizers are registered explicitly. The disposable probe CRD is maintained in `deploy/framework-probe-crd.yaml`; production structural CRDs, RBAC and CEL admission are reviewed chart resources. This workflow does not require KubeOps CLI generation.

`FrameworkProbe` belongs to the separate `spikes.ha-operator.io/v1alpha1` API group. It accepts a bounded value and a hold barrier. Reconciliation first persists `Accepted` status, then projects the value into the installation's fixed `framework-probe-state` ConfigMap and records `Completed`. A held intent remains durable while the process restarts. This tests framework recovery; it is not a Supervisor job or a Core lifecycle operation.

KubeOps watches only the explicit installation namespace. Its default ambient client configuration is replaced before framework registration. The probe is disabled by default and requires the installed workload's explicit in-cluster credential opt-in and a valid namespace. Local API runs register neither the framework nor its Kubernetes client. The development fixture enables it with the downward-API namespace.

The operator can read/watch/update probes and update their status within that namespace. It can read/update only the fixed probe ConfigMap. It cannot create probes, create ConfigMaps, read Secrets, modify Core workloads or watch resources outside its namespace. Administrators install the CRD and acceptance fixture through the guarded project cluster.

Reconciliation re-reads current intent, checks namespace/name/UID, and uses resourceVersion-checked replacements. Conflicts requeue; a projection owned by another UID is refused. The finalizer clears only its own projection and retains the finalizer while the explicit cleanup barrier is set. These checks do not establish production operation fencing: CAS on a ConfigMap does not fence a running Core process, and a namespace-scoped probe name constraint does not reject another installation elsewhere in a cluster.

## Framework integration findings

KubeOps 13.3.1 auto-attaches a finalizer name derived from the entity group and finalizer class name, while deletion dispatch resolves a keyed DI registration by the attached name. The registration must therefore use `spikes.ha-operator.io/probefinalizer`. A regression test checks that the registered key matches the framework's generated identifier. The first real-cluster run exposed this mismatch and returned exit 1 with successful teardown; the finalizer test was retained and the registration corrected.

## Core lifecycle implementation

The chart under `charts/home-assistant-supervisor-operator` now defines structural `ha-operator.io/v1alpha1` instance and operation CRDs, status subresources, namespace-scoped RBAC, and cluster admission policies. The fixed singleton instance is `home-assistant`. Fixed cluster policy names and Helm ownership reject another installation; admission rejects another instance name/namespace and scaling the API or Core above one. The API Deployment uses `Recreate`; Core uses an `OnDelete` StatefulSet. Controller creation permissions cannot use Kubernetes `resourceNames`, so admission constrains the operator service account to its fixed workload.

The installed process explicitly enables KubeOps and in-cluster credentials for its downward-API namespace. Local API execution remains disabled by default. API handlers commit a command to the instance with a resourceVersion check before waiting. Reconciliation creates its operation record, waits for graceful termination before restart, and gates startup on Pod readiness and stock Core's private socket reporting `RUNNING`. Request cancellation ends HTTP waiting, not the accepted operation. Optional `Idempotency-Key` retries recover the same durable command. Jobs expose retained progress; current Pod logs are limited to 1,000 lines. Historical boots and following logs are deferred.

Every StatefulSet write carries instance UID and monotonic generation fencing plus Kubernetes resourceVersion. Pod templates also carry the instance UID; reconciliation and finalization require the Pod controlling owner reference to match the current StatefulSet UID and the Pod annotation to match the instance UID. A surviving Pod without its StatefulSet blocks recreation and finalizer completion. Pods from earlier unpublished development builds without the ownership annotation fail closed and require verified graceful termination before recreation. An unreachable or terminating old Pod blocks replacement. Kubernetes selects Core placement according to scheduling and PV constraints; the instance has no selected-node field and the operator injects no node selector. The operator never force-deletes a Pod or bypasses storage constraints. A template upgrade stops Core and, if needed, recreates the StatefulSet only after the old Pod is absent. Physical node fencing remains an administrator responsibility. The kind fault test disconnects only the sealed project worker, proves the old Core process remains alive without replacement, stops that worker to establish a physical fence, then reconnects that node to complete normal termination while keeping it cordoned. Core recovers on the other sealed node using the same PVC/PV and retained configuration. The test PVC uses a project-owned shared filesystem mounted into both nested kind nodes; it validates scheduler/controller recovery, not production CSI attachment, SQLite reliability on network storage, hardware availability or LAN discovery. A node-local PV still prevents cross-node scheduling; choose a suitable portable storage backend for that behavior.

`ownership: Ui` permits lifecycle/options requests. `ownership: GitOps` rejects changing UI requests; edit the CR specification instead. Bootstrap callbacks that repeat existing options remain valid. The native Core configuration file belongs to Core and the user; the chart copies its initial file only when none exists. It does not overwrite restored files or recursively change their permissions. The independently owned `instance-data` PVC has Helm's keep policy and no CR owner reference. Finalization and a pre-delete shutdown Job stop Core before removing its workload, retaining the PVC and its configuration. Uninstall can fail closed if a node is unreachable; fence and recover it before retrying.

## Installing the development preview

Only Kubernetes 1.37.0 on the pinned Linux kind profile is tested. This is a development preview; add-ons, ingress authentication, updates and backups/restores require later milestones. The first tagged preview, [v0.1.0-alpha.1](https://github.com/anhaehne/home-assistant-supervisor-operator/releases/tag/v0.1.0-alpha.1), publishes public GHCR operator/gateway images pinned by digest, a Helm OCI chart and a checksummed manifest bundle. Anonymous downloads and a fresh published-chart installation passed on 2026-10-04. Publish the operator and gateway with the pinned .NET SDK into `.build/operator` and `.build/gateway`, build with `dev/Operator.Dockerfile` and `dev/Gateway.Dockerfile`, publish the images to your own registry, and supply immutable references. For the guarded local environment, `./hack/dev-build.sh` builds and loads them and `./hack/dev-install.sh` installs the chart after the P0 Core fixture is stopped.

An installation administrator supplies one namespace, an existing credentials Secret with separate random `core-token` and `gateway-token` keys and a working StorageClass. The stock Core image and entrypoint are retained. Its initial configuration includes `default_config`; the Supervisor environment loads native `hassio` and its port-80 listener. Normal configuration changes remain native Core work. The chart requires permission to install its CRDs and cluster admission policies; the running operator has no Secret-read permission. With the default Pod-network trust enabled, it also receives read-only get/list access to cluster nodes; disabling that option removes this cluster permission.

```sh
helm install haso ./charts/home-assistant-supervisor-operator \
  --namespace home-assistant --create-namespace \
  --set operatorImage=YOUR_REGISTRY/operator@sha256:YOUR_DIGEST \
  --set gatewayImage=YOUR_REGISTRY/gateway@sha256:YOUR_DIGEST \
  --set credentialsSecret=YOUR_EXISTING_SECRET \
  --set storageClassName=YOUR_STORAGE_CLASS
```

Keep credentials out of values files, command-line literals, logs and source control. Provision the Secret before installing; `--create-namespace` cannot create a Secret for you. The optional `operatorNode` controls API placement independently of Core. Expose only the `core` Service for the frontend. The optional ingress values require an existing ingress controller, host and TLS Secret; configure the actual proxy's trusted addresses using `ingress.trustedProxies` as described below. Supervisor and gateway Services are internal credential-bearing APIs, not public frontend backends.

Use `helm upgrade` for application/chart changes. When upgrading from the pinned alpha, apply the new instance CRD before the controller/chart upgrade. The legacy template hash triggers graceful workload replacement to remove the injected selector while retaining the PVC. Helm does not upgrade CRDs in the `crds/` directory: review schema compatibility, apply the supplied CRD files as administrator before upgrading, and retain supported optional defaults. P1 tests missing optional fields in the initial v1alpha1 schema; it does not claim migration between historical production CRD versions. PVC size expansion depends on the StorageClass; cross-node recovery requires storage that supports access from the replacement node. Supply `operatorBuildId` only for local mutable development tags so the Deployment actually reloads the new build. Immutable image references normally supply their own rollout identity.

`helm uninstall haso --namespace home-assistant --wait --timeout 10m` invokes graceful shutdown and retains `instance-data`; Helm also retains CRDs. Reinstall with the same release, namespace, storage and credentials to reuse that PVC. Remove retained data or cluster CRDs only as a separate deliberate administrator action after inspecting them. Do not delete a stuck Pod to get around fencing.

Current acceptance scripts are `test-lifecycle.sh`, `test-upgrades.sh`, `test-dependency-recovery.sh`, `test-node-fault.sh` and `test-api-recovery.sh`, invoked serially by `test-p1.sh` after P0's native browser scenarios. Diagnostics export fixed namespace metadata/status and redacted logs, never CR options, Secrets or kubeconfig. The fresh full suite `.test-artifacts/p0.zEExGB/suite-result.json` records `exit_code: 0` and `teardown_complete: true`; `p1.log` records all five gates. The chart admits scale-to-zero when Kubernetes omits its zero-valued ScaleSpec replicas field, while rejecting more than one replica. The required injected-failure cleanup wrapper passed with inner exit 41 and successful teardown in `.test-artifacts/p0.udReFG/`. Interrupted runs remain incomplete evidence.

Reconciliation uses explicit bounded-delay retries and a 15-second resync of only the fixed singleton. Both controller dependency failures and framework reads can therefore recover without a watched instance change. Resync uses the normal serial KubeOps queue and finalizer pipeline; it cannot choose another target or skip workload fencing. Acceptance removes the workload template and separately revokes instance GET for more than the framework's default error-retry window, then restores each dependency without an instance event.

The unpinned source passed fresh full acceptance on 2026-10-04 in `.test-artifacts/p0.VS5OM8/`: 112 unit tests, all browser/P1 gates, legacy selector removal and cross-node recovery with unchanged PVC/PV and configuration. `suite-result.json` records exit zero and complete teardown of both sealed nodes and their node/shared test data volumes. The published alpha still has the prior placement requirement.

## Trusted ingress proxies

Current source recommends and defaults to `ingress.trustPodNetwork: true` for first installation and upgrades of an existing PVC. The operator discovers node Pod CIDRs and manages native proxy trust for all those ranges. This feature is included in the alpha.3 candidate, absent from alpha.2, and the new discovery default passed isolated acceptance. It also works with externally managed Gateway API routes when `ingress.enabled` is false. To restrict trust to explicit reverse proxy source IPs or narrow CIDRs, disable discovery in your installation values:

```yaml
ingress:
  trustPodNetwork: false
  trustedProxies:
    - 10.0.0.5/32
    - 10.0.0.6/32
```

With `trustPodNetwork: true`, the effective trusted proxies are the union of discovered Pod networks and any explicit `trustedProxies` entries; an empty explicit list does not revoke the discovered trust. Discovery requires administrator permission to install the fixed `supervisor-pod-network` ClusterRole and ClusterRoleBinding, granting only get/list access to nodes to the installation's `supervisor` ServiceAccount. Nodes are polled through the existing 15-second singleton resync; no node watch or cross-namespace Secret access is granted. The CRD defaults discovery to false for older instances; the Helm chart explicitly enables it for new installations and upgrades.

Discovery requires populated, authoritative `node.spec.podCIDRs` and an ingress peer whose source address actually belongs to those ranges. Some CNI configurations, including Calico configurations with separate IP pools, may not publish authoritative node Pod CIDRs. If discovery cannot establish the ranges or they do not cover Core’s Pod address, convergence fails clearly; it never guesses a private network. Use `trustPodNetwork: false` with explicit `trustedProxies` for these clusters, external proxies or host-network ingress peers. Trusting all Pod ranges grants every workload there permission to supply client addresses.

With `trustPodNetwork: false`, `trustedProxies: null` leaves native HTTP settings unmanaged; a nonempty list enables forwarded headers only for those sources, and `[]` explicitly disables proxy trust. Addresses are normalized and deduplicated; unrestricted /0 networks, malformed addresses and networks with host bits are rejected. Choose stable source addresses or narrowly scoped controller networks that your ingress deployment actually uses.

For a fresh installation, include that values file in the normal Helm install. For an existing installation, review and apply **both** updated CRDs before upgrading the chart and operator/gateway images. Helm does not upgrade chart CRDs automatically. The instance schema adds managed proxy settings, discovery intent and status, accepted-command generation/network revision and management history; the operation schema adds the configuration phase and durable trial fingerprint. With a reviewed fixed chart and its matching images:

```sh
kubectl --context "$KUBE_CONTEXT" apply -f ./charts/home-assistant-supervisor-operator/crds/
helm --kube-context "$KUBE_CONTEXT" upgrade haso ./charts/home-assistant-supervisor-operator \
  --namespace home-assistant --values YOUR_INSTALLATION_VALUES.yaml --wait --timeout 10m
kubectl --context "$KUBE_CONTEXT" --namespace home-assistant wait \
  --for=condition=Ready homeassistantinstance/home-assistant --timeout=10m
```

Include all original installation values, credentials Secret references, storage settings and matching immutable image references in the values file. Do not reinstall alpha.2 expecting this setting to take effect.

Home Assistant 2026.9.4 migrates YAML HTTP configuration into its native store once; adding YAML later does not replace the active migrated settings. The operator uses the stock Core's authenticated native HTTP WebSocket configuration API through its private Supervisor socket. It preserves unrelated HTTP settings and configuration files, persists the intended trial fingerprint, performs fenced graceful Core replacement, waits for native application health and confirms the active trial. It never edits Core's private storage files. See the [native HTTP documentation](https://www.home-assistant.io/integrations/http/) and [pinned HTTP configuration implementation](https://github.com/home-assistant/core/blob/2026.9.4/homeassistant/components/http/config.py).

Stock Core has no direct trusted-proxy environment variable. YAML can use [`!env_var`](https://www.home-assistant.io/docs/configuration/yaml/#environment-variables), but HTTP YAML is still imported only once, so changing an environment value cannot reconfigure a migrated PVC. Helm values plus the native API provide the external configuration path.

While discovery or an explicit proxy list is managed, let the operator exclusively manage native HTTP configuration. Native configure/promote commands have no atomic comparison parameter: local checks reject known unrelated trials, but cannot fence simultaneous writes from a native administrator. Avoid native HTTP UI/API edits during convergence. To return ownership to native Core, first wait for the managed change to become Ready, then set `trustPodNetwork: false` and `trustedProxies: null`, upgrade and wait for Ready again. This leaves the last confirmed settings intact; set `trustPodNetwork: false` with `trustedProxies: []` and wait for Ready before releasing ownership if you intend to revoke trust. An unrelated or failed native trial blocks confirmation and is reported in the instance condition rather than silently approved.

For a Running instance, Ready verifies Core application health and convergence of managed proxy settings. Changes while Core is intentionally Stopped are applied when it next starts. It does not validate your DNS, TLS, Gateway routes or frontend authentication. `hack/test-ingress-proxy.sh`, included in the full P1 suite, tests actual forwarded frontend requests from separate trusted and untrusted proxy Pods, changes and revocation on an already migrated/onboarded PVC, and a fresh installation followed by Core replacement. It verifies native settings and retained configuration, ownership records and PVC identity without writing Core's private store.

The supervisor Deployment and graceful shutdown hook now declare `runAsNonRoot` and `RuntimeDefault` seccomp explicitly, addressing the separately reported PodSecurity warnings. Core and gateway still require their native private-socket permissions; this does not establish full-chart compatibility with the restricted PodSecurity profile.
